## Step 2 — Provenance

all-definition retention, scoped project overrides and project persistence were
retained. No source winner or author is inferred from traversal order, namespace,
matching JSON, or physical container metadata. Static load priority remains unknown.

Added `RuntimeRecipeObservation`: recipe ID, runtime type, serializer, snapshot ID,
collection time and source information. `RecipeProvenance` carries this evidence
separately from physical static candidates and exposes runtime confirmation.
It rejects observations with a different Recipe ID or a non-runtime scope and
requires an actual runtime source for runtime provenance. `RecipeMergeService`
populates these fields from the existing Companion DTO; normalized properties and
other adapter metadata remain intact on its existing runtime entry. The protocol,
snapshot schema and project format versions are unchanged.

## Step 3 — Export capabilities

Added `ExportCapabilityResolver` as the existing planner's common capability entry
point. It checks profile/environment agreement, quarantined IDs, original source
references, the registered format adapter and its allowed operations. Checks are
read-only; generation remains in the existing exporters. Missing adapters produce
an explained `UNKNOWN`, never a successful export. `ExportPlanner` resolves each
format once per change and excludes unsupported changes from file generation and
target-file lists. This fixes previews that previously displayed a supported
capability and target paths for a quarantined change while reporting an error
elsewhere in the same plan.

`VanillaExportSupport` now checks serializer identity against the raw JSON and
reparses required properties instead of trusting an earlier `PARSED` flag. It
rejects object-valued cooking results for the checked 1.20.1 serializers and air
outputs based on the actual JSON as well as parsed metadata. The existing KubeJS
projection retains ordinary unknown root fields losslessly, but custom nested
semantics, conditions and namespaced extensions still require verified adapters.
No support decision depends on the recipe namespace or archive mod ID.

The official KubeJS documentation was consulted:
[Recipe editing](https://kubejs.com/wiki/tutorials/recipes),
[server_scripts](https://kubejs.com/wiki/folder-structure/server-scripts),
[data](https://kubejs.com/wiki/folder-structure/data).
These document `ServerEvents.recipes`, custom JSON recipes and reloadable data;
they are not a guarantee for every serializer/version. The existing version gate
remains Minecraft 1.20.1 Forge with KubeJS `2001.6.4-build.120` or
`2001.6.5-build.26`, determined from imported mod metadata.

### Effective existing support after Step 3

For the checked Minecraft/KubeJS environments. CREATE/UPDATE/DELETE columns refer
to JS; Data JSON supports CREATE/UPDATE only. These mechanisms predate this phase.

| Recipe Type | JS | Data JSON | CREATE | UPDATE | DELETE |
|---|---|---|---|---|---|
| Crafting Shaped | yes | yes | yes | yes | yes |
| Crafting Shapeless | yes | yes | yes | yes | yes |
| Smelting / Blasting / Smoking / Campfire | yes | yes | yes | yes | yes |
| Stonecutting | yes | yes | yes | yes | yes |
| Smithing Transform / Trim | yes | yes | yes | yes | yes |
| GregTech | restricted adapter* | no | restricted* | restricted* | restricted* |
| Create | no verified export adapter | no | no | no | no |
| Mekanism | no verified export adapter | no | no | no | no |

*Existing GTCEu 7.1.4 + KubeJS 2001.6.4-build.120 adapter only, subject to its
property checks. Conditions, research and additional properties remain unsupported.
The ISG GTCEu 8 snapshot is not covered. No new GT/Create/Mekanism support is claimed.
Modes already present are `JAVASCRIPT`, `DATA_JSON`, `COMBINED`, `AUTO` (Automatic).
This iteration does not rename the persisted `AUTO` enum or redesign mode selection.
